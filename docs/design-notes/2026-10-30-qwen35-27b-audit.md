## 2. What the GDN layer needs, against what exists

The recurrence (GAP-368): per value head, decay `g = -exp(A_log) * softplus(a + dt_bias)`, strength `beta = sigmoid(b)`,
state `S_t = S_{t-1} (I - beta k k^T) + beta k v^T` in **f32**, output `o_t = S_t q_t`, a depthwise causal conv over the
q/k/v channels first, and a gated RMS norm after.

| Piece | CPU | CUDA | Vulkan | Source |
|---|---|---|---|---|
| depthwise causal conv1d (`OpKind::CausalConv1d`) | yes | yes | **no contract, no kernel** | READ `cpu/ssm.fkc.md`, `cuda/causal_conv1d.fkc.md`; no `vulkan/` file names it |
| `SelectiveScan` / `SsdChunkScan` | yes | yes | no | READ; Mamba math, **not** the delta rule (row 40) |
| `CumSum`, `Tril`, `Triu` | yes | yes | yes (`vulkan_dispatch.rs` wrappers; SPIR-V `cumsum_*`, `tril_*`, `triu_*`) | READ contracts under `kernel-contracts/{cpu,cuda,vulkan}`, `vulkan_dispatch.rs` |
| softplus, L2 norm | composed (Exp/Log/Add/Where; Sqr/SumReduce/Rsqrt) | same | same | READ the `OpKind` list: no `Softplus`, no `L2Norm` |
| `Op::Scan` (a loop with carried state) | no native kernel ("Phase 1", `pipelined.rs`) | no | no | READ |
| gated-delta-rule update | **none** | **none** | **none** | GAP-368 |

So a correct-but-slow path is expressible from base ops (the plan in issue #341 and row 40), but two pieces have no
shortcut: the conv on Vulkan (composable as 4 shifted multiply-adds for kernel size 4, **NOT MEASURED**), and the
**chunk loop**, which is data-independent but unrolls into the graph unless `Op::Scan` gets a native kernel or a fused
kernel replaces it.

**Prefill node count (ARITHMETIC from a hand count of the composed ops, NOT MEASURED).** Per GDN layer, chunkwise
parallel with chunk 64: about 70 fixed nodes (projections, conv, norm, gate, out) plus about 45 per chunk (cumulative
decay and mask, `beta K K^T` masked, the unit-lower-triangular inverse by repeated squaring, the two solves, the
inter-chunk read and state update). For 145 tokens (3 chunks): about 205 per layer, about 9.8k for 48 layers, about
10.5k with the 16 attention layers. For 4096 tokens (64 chunks): about 2,950 per layer, about 141k for 48 layers. The
first is workable; the second is not, and is the case for a fused chunked kernel (stage 3) rather than a bigger graph.
The first deliverable of the composed path must replace these estimates with a measured node count.

**Decode.** One recurrence step per GDN layer per token is about 25 nodes composed (rank-1 update of `S`, a matvec,
elementwise gates), so about 1.2k nodes for 48 layers plus the attention layers; plan-once decode (Phase D) should make
that a one-time cost, **if** the plan can carry recurrent state, which is the next item.

## 3. Decode state: the scheduler assumes uniform KV

**READ** `fuel-inference/src/multi_session.rs` `DecodeModel::layer_state_specs` is collapsed to one
`(n_kv_heads, head_dim)` by `LayerStateSpec::collapse_uniform`, which **fails loudly** for a model whose layers are not
uniform per-head KV (the MLA guard, GAP-166). `LayerStateSpec` has `KeyValue` and a general `Slots(Vec<StateSlot>)`
(built for MLA's latent cache). **CORRECTED (row 117 design note): `Slots` is a PER-TOKEN, GROWING buffer, so it can NOT
describe a GDN layer's fixed-size state; a new variant is needed (`2026-10-30-hybrid-decode-state-row-117.md`).** The scheduler path that consumes it for a
hybrid (16 KV layers plus 48 recurrent layers) does not exist. **READ** `lazy_mamba2.rs` (587 lines) runs a whole
sequence per call and keeps no decode state, so there is no in-tree precedent for a persistent recurrent state.

State size, **ARITHMETIC** assuming `dk = dv = 128`: S is `48 x 128 x 128 x 4 B` = 3.1 MB per GDN layer, about 151 MB
across 48 layers per sequence; the conv state is `conv_dim x (K-1)` with `conv_dim = 2*16*128 + 48*128 = 10,240` and
`K = 4`, about 123 KB per layer in f32. The KV cache for the 16 attention layers depends on the 27B's KV head count
(NOT READ).

## 4. Weights, memory, and which path fits the rig

**ARITHMETIC** (27e9 parameters): bf16 about 54 GB; Q8_0 about 28.7 GB; Q4_K_M about 16 GB (4.85 bits per weight, a
typical figure, **NOT MEASURED** for this model). Row 40 names the driver as a VII + A770 pipeline split (about 32 GB of
VRAM in total if both are the 16 GB cards); the desktop rig CireSnave is reassembling is **not described to me**, so its
VRAM is an open input. bf16 does not fit any plausible pair; Q4_K_M plausibly does, with room for state and KV; Q8_0
only on 32 GB or more.

- **READ** the token embedding is held as f32 (`vocab 248320 x hidden 5120` is 5.1 GB; a tied head adds a copy, row 40).
  That alone is a third of a Q4_K_M model's size and must be budgeted or stored narrower.
- **READ, and the largest finding of this audit:** `WeightStorage` (`fuel-tensor/src/lazy.rs`) has `F32`, `BF16`,
  `Q4_0` and `Awq`, and nothing else. `QuantizedLlama3Model::from_gguf` keeps **only `Q4_0`** tensors quantized and
  "dequantizes other GGML dtypes to F32" (`lazy_quantized_llama.rs`, `match dt { Q4_0 => ..., _ => dequant_bytes_to_f32 }`).
  So a Q4_K_M, Q6_K, Q8_0 or f16 GGUF is expanded to **f32 at load** on this path: a 27B Q4_K_M file (about 16 GB)
  would become about 108 GB of f32 (ARITHMETIC: 27e9 x 4 B), which fits no rig. This also explains Lightbulb's
  measurement that SmolLM2-135M f16 and Q8_0 GGUFs have the same device footprint (both f32). Native Q8_0 is the
  draft PR #495, held on row 105. **No K-quant can stay quantized end to end today**, so row 124 (below) is on the
  critical path of the quantized route, ahead of the Vulkan kernels of row 119.
- **READ** Vulkan `QMatMul` (`vulkan/qmatmul.fkc.md`): Q4_0 has fused kernels (`qmatvec_q4_0`, `matmul_q4_0_tiled`);
  **Q4_K_M and Q8_0 dequantize the whole weight to an f32 scratch buffer and then run a dense matmul**; Q4_1, Q5_*, Q2K,
  Q3K, Q5K, Q6K and Q8_1 are not wired on Vulkan (GAP-064: they go to the CPU). A Q4_K_M GGUF therefore decodes through a
  per-use dequantize on Vulkan today. Whether that is fast enough is **NOT MEASURED**; it is the likely first bottleneck.
- **READ** row 67 (larger-than-VRAM, I1/I2) provides a device budget and eviction; row 107 (the per-op table) is the
  instrument that would show where a first run spends its time.

## 4b. The rig (CireSnave, 2026-10-30, verbatim) and what it changes

> "My desktop PC has an RTX 4060, and a PEX switch hosting 4 external PCIe slots which currently have my Radeon VII, an
> Intel Arc A770, and one P40, and I have both another P40 and an MI50 (32GB) ordered. I will dual boot that PC on
> Windows and Linux so we can switch to test on both O/Ss."

**ARITHMETIC** (file sizes are the PM's figure, 15.3 GiB for Q4_K_M, NOT MEASURED by me): Q4_K_M fits ONE 24 GB P40 or
the 32 GB MI50 with room for KV and f32 GDN state; Q8_0 (about 28.7 GB, section 4) fits only the MI50 and tightly. So the
multi-device pipeline split (rows 114, 120, 121) is **off the critical path**; it stays a later option (Q8_0/bf16, two
cards), not the first target.

**READ (Baracuda `origin/main@7823c6c3`, sibling reference only), and the finding that matters most here:**
- Baracuda's hand-written kernel crates (`baracuda-kernels-sys`: GEMM, mmvq quantized matvec, attention) target **sm_80 and
  newer**; its README lists "<= sm_75 (Turing, Volta, Pascal) unsupported by the hand-written kernel crates". A P40 is
  **sm_61**. So today the CUDA kernels a Fuel `--features cuda` build links do not load on a P40.
- The sm_61 route is Baracuda's emitter/NVRTC path (SA-12 done, SA-13 "sm_61 through the latest, Phase B" **open**:
  "compile emitted kernels for sm_61 and run them on a P40 (held(P40 hardware); host NVRTC 13.x rejects sm_61, 12.9 is
  needed)"). Nobody has run a kernel on sm_61 yet. Baracuda's own README: "don't read this as sm_61 works today."
- Pascal facts for that work: `__dp4a` exists from sm_61 (the Q4_K/Q8_0 matvec dot can use it); native fp16 arithmetic is
  slow on sm_61 (the emitter already picks `HalfArith::ViaF32`); there are **no tensor cores**, so every WMMA/`mma.sync`/
  `cp.async` kernel is unusable and sm_61 needs SIMT paths.
- **READ (Fuel):** no `sm_61`/Pascal string exists in this repo; `fuel-cuda-backend/src/probe.rs` records the compute
  capability but nothing selects kernels by it. Whether Fuel's CUDA backend even constructs on a P40 is **NOT MEASURED**.
- **READ (AMD):** Fuel has no ROCm/HIP backend; `Rocm` appears only as a topology enum variant (`fuel-parallel/src/topology.rs`).
  Baracuda has no HIP crate. **MI50 and Radeon VII are the same GPU (Vega 20, gfx906)**, so the MI50 and the VII are
  reached through **Vulkan**, which Fuel already has. Whether the Windows AMD driver exposes Vulkan on an MI50 (a compute
  card with no display outputs) is **NOT MEASURED**; the Linux route (Mesa RADV on gfx906) is **unmeasured here** too.
- **READ (Fuel Vulkan):** a Q4_K_M weight is dequantized to an f32 scratch buffer per use and then a dense matmul runs
  (section 4, GAP-064); K-quants stay unquantized-to-f32 at load until row 124. So the first Vulkan token on a 32 GB MI50
  needs row 124 (resident K-quants) for the memory fit and row 119 (fused K-quant matvec) for any acceptable speed.
- **READ:** `gpu_id` is a per-backend enumeration ordinal (`probe.rs` in both GPU backends), not a hardware identity.
  With a 4060, a P40, a VII/MI50, an A770 and a CPU present, CUDA ordinals and Vulkan ordinals name overlapping hardware
  (the 4060 and the P40 are both a CUDA device and a Vulkan device), and `new_device()` picks `PreferDiscrete`. Selecting
  "the MI50" or "the P40 over the 4060" needs an explicit, stable selector (PCI bus id or device UUID matched across the
  two APIs); that selector does not exist. That is ROADMAP row 125; the Linux GPU scripts are row 126.

**Reordered first targets (re-derived from the above; the PM's reading was a starting point):**
1. **Single-card Vulkan on the 32 GB MI50 (or the VII at 16 GB for the small checkpoints)** is the first end-to-end target
   that needs no Baracuda or Unpopped work: rows 124, 115, 117, 118, then 119.
2. **Single-card CUDA on the P40** is gated on Baracuda SA-13 (sm_61 emit, NVRTC 12.9) and a P40 box; it is a request
   to Baracuda through the PM, not Fuel code. Meanwhile the **RTX 4060 (sm_89, 8 GB)** runs the CUDA path on every
   structurally identical test with a small checkpoint (the 0.8B file), so rows 115/117/118 are verified there first.
3. **Vulkan on the Arc A770 (16 GB)** after the MI50: the 27B at Q4_K_M (15.3 GiB) does not leave room for state on 16 GB.
4. Multi-device (rows 114, 120, 121): deferred; row 114's probe remains cheap and useful, but nothing waits on it.

**Which rows need Linux, which need Windows (the rig dual-boots):**
- **Either OS, no GPU:** rows 115, 116, 117, 118, 124 (CPU oracle and loader work). CI already covers ubuntu, macOS and windows.
- **Windows (where this box and the current gates live):** the 4060 CUDA and the VII Vulkan runs; `gpu-run.ps1` and
  `cuda-build.ps1` are PowerShell and Windows-shaped.
- **Linux required:** any CUDA run on the P40 is expected to be easier there (NVRTC 12.9 install, no WDDM; the P40 is a
  compute card), and Vulkan on gfx906 via RADV and on the A770 via ANV is the Linux side of rows 119/121. **Fuel has no
  Linux GPU runner script**, so a Linux equivalent of `gpu-run`/`cuda-build` (mutex, slot protocol) is itself new work (row 126)
  that nothing owns yet. Whether Fuel's GPU backends build and pass their live tests on Linux is **NOT MEASURED**
  (CI builds Linux without GPU features).

## 5. Multi-GPU pipeline split

- **READ** `DeviceLocation` carries `Vulkan { gpu_id }`, so the IR can name a second Vulkan device.
- **READ** `pipelined_bridge.rs`: the single-device realize refuses a `Vulkan { gpu_id }` it has no handle for, and
  `seed_extra_device_handles` de-duplicates extra devices **by `BackendId`**, so two GPUs of one backend (VII + A770 are
  both Vulkan) are not representable there. The multi-device realize was built for one device per vendor (CUDA +
  Vulkan). **Whether two Vulkan devices can run one graph is NOT MEASURED**; the reading above says it cannot today.
- Cross-stage traffic: the two cards share no peer-to-peer path I can name, so a stage boundary is a device-to-host-to-
  device copy of one hidden-state tensor per token (`hidden x 4 B` = 20 KB at hidden 5120, **ARITHMETIC**); at decode
  that is small next to the weight reads, at prefill it scales with the prompt.
- Row 40 already asks whether per-stage placement exists on Vulkan; this audit's answer is: the placement type exists,
  the handle plumbing for two same-backend devices does not appear to, and a probe test settles it cheaply.
- GPU runners on both machines are wanted (CireSnave); that is infrastructure the PM and CireSnave own, with a Fuel-side
  test plan below.

## 7. What this note does not settle

- The rig is now described (section 4b); its fit statements still rest on the PM's 15.3 GiB figure, not on a file I measured.
- The 27B's head dimensions, KV heads, hidden and intermediate sizes (not fetched).
- Whether a `qwen35` GGUF's tensor layout matches the HF safetensors layout the loader reads.
- Any speed. There is no first run, so there is no number; the composed path is "correct but slow" by construction.
- Whether "Qwen 3.8" is `Qwen/Qwen3.5-27B` (row 40's reading) or a later checkpoint with a different config; the
  loader is config-driven, but a changed layer pattern or head layout would change rows 115 and 117.
