## 2. What the GDN layer needs, against what exists

The recurrence (GAP-368): per value head, decay `g = -exp(A_log) * softplus(a + dt_bias)`, strength `beta = sigmoid(b)`,
state `S_t = S_{t-1} (I - beta k k^T) + beta k v^T` in **f32**, output `o_t = S_t q_t`, a depthwise causal conv over the
q/k/v channels first, and a gated RMS norm after.

| Piece | CPU | CUDA | Vulkan | Source |
|---|---|---|---|---|
| depthwise causal conv1d (`OpKind::CausalConv1d`) | yes | yes | **no contract, no kernel** | READ `cpu/ssm.fkc.md`, `cuda/causal_conv1d.fkc.md`; no `vulkan/` file names it |
| `SelectiveScan` / `SsdChunkScan` | yes | yes | no | READ; Mamba math, **not** the delta rule (row 40) |
| `CumSum`, `Tril`, `Triu` | yes | yes | yes (`vulkan_dispatch.rs` wrappers; SPIR-V `cumsum_*`, `tril_*`, `triu_*`) | READ contracts under `kernel-contracts/{cpu,cuda,vulkan}`, `vulkan_dispatch.rs` |
| softplus, L2 norm | composed (Exp/Log/Add/Where; Sqr/SumReduce/Rsqrt) | same | same | READ the `OpKind` list: no `Softplus`, no `L2Norm` |
| `Op::Scan` (a loop with carried state) | no native kernel ("Phase 1", `pipelined.rs`) | no | no | READ |
| gated-delta-rule update | **none** | **none** | **none** | GAP-368 |

So a correct-but-slow path is expressible from base ops (the plan in issue #341 and row 40), but two pieces have no
shortcut: the conv on Vulkan (composable as 4 shifted multiply-adds for kernel size 4, **NOT MEASURED**), and the
**chunk loop**, which is data-independent but unrolls into the graph unless `Op::Scan` gets a native kernel or a fused
kernel replaces it.

**Prefill node count (ARITHMETIC from a hand count of the composed ops, NOT MEASURED).** Per GDN layer, chunkwise
parallel with chunk 64: about 70 fixed nodes (projections, conv, norm, gate, out) plus about 45 per chunk (cumulative
decay and mask, `beta K K^T` masked, the unit-lower-triangular inverse by repeated squaring, the two solves, the
inter-chunk read and state update). For 145 tokens (3 chunks): about 205 per layer, about 9.8k for 48 layers, about
10.5k with the 16 attention layers. For 4096 tokens (64 chunks): about 2,950 per layer, about 141k for 48 layers. The
first is workable; the second is not, and is the case for a fused chunked kernel (stage 3) rather than a bigger graph.
The first deliverable of the composed path must replace these estimates with a measured node count.

**Decode.** One recurrence step per GDN layer per token is about 25 nodes composed (rank-1 update of `S`, a matvec,
elementwise gates), so about 1.2k nodes for 48 layers plus the attention layers; plan-once decode (Phase D) should make
that a one-time cost, **if** the plan can carry recurrent state, which is the next item.

## 3. Decode state: the scheduler assumes uniform KV

**READ** `fuel-inference/src/multi_session.rs` `DecodeModel::layer_state_specs` is collapsed to one
`(n_kv_heads, head_dim)` by `LayerStateSpec::collapse_uniform`, which **fails loudly** for a model whose layers are not
uniform per-head KV (the MLA guard, GAP-166). `LayerStateSpec` has `KeyValue` and a general `Slots(Vec<StateSlot>)`
(built for MLA's latent cache), so the type can describe a GDN layer's state; the scheduler path that consumes it for a
hybrid (16 KV layers plus 48 recurrent layers) does not exist. **READ** `lazy_mamba2.rs` (587 lines) runs a whole
sequence per call and keeps no decode state, so there is no in-tree precedent for a persistent recurrent state.

State size, **ARITHMETIC** assuming `dk = dv = 128`: S is `48 x 128 x 128 x 4 B` = 3.1 MB per GDN layer, about 151 MB
across 48 layers per sequence; the conv state is `conv_dim x (K-1)` with `conv_dim = 2*16*128 + 48*128 = 10,240` and
`K = 4`, about 123 KB per layer in f32. The KV cache for the 16 attention layers depends on the 27B's KV head count
(NOT READ).

## 4. Weights, memory, and which path fits the rig

**ARITHMETIC** (27e9 parameters): bf16 about 54 GB; Q8_0 about 28.7 GB; Q4_K_M about 16 GB (4.85 bits per weight, a
typical figure, **NOT MEASURED** for this model). Row 40 names the driver as a VII + A770 pipeline split (about 32 GB of
VRAM in total if both are the 16 GB cards); the desktop rig CireSnave is reassembling is **not described to me**, so its
VRAM is an open input. bf16 does not fit any plausible pair; Q4_K_M plausibly does, with room for state and KV; Q8_0
only on 32 GB or more.

- **READ** the token embedding is held as f32 (`vocab 248320 x hidden 5120` is 5.1 GB; a tied head adds a copy, row 40).
  That alone is a third of a Q4_K_M model's size and must be budgeted or stored narrower.
- **READ** Vulkan `QMatMul` (`vulkan/qmatmul.fkc.md`): Q4_0 has fused kernels (`qmatvec_q4_0`, `matmul_q4_0_tiled`);
  **Q4_K_M and Q8_0 dequantize the whole weight to an f32 scratch buffer and then run a dense matmul**; Q4_1, Q5_*, Q2K,
  Q3K, Q5K, Q6K and Q8_1 are not wired on Vulkan (GAP-064: they go to the CPU). A Q4_K_M GGUF therefore decodes through a
  per-use dequantize on Vulkan today. Whether that is fast enough is **NOT MEASURED**; it is the likely first bottleneck.
- **READ** row 67 (larger-than-VRAM, I1/I2) provides a device budget and eviction; row 107 (the per-op table) is the
  instrument that would show where a first run spends its time.

## 5. Multi-GPU pipeline split

- **READ** `DeviceLocation` carries `Vulkan { gpu_id }`, so the IR can name a second Vulkan device.
- **READ** `pipelined_bridge.rs`: the single-device realize refuses a `Vulkan { gpu_id }` it has no handle for, and
  `seed_extra_device_handles` de-duplicates extra devices **by `BackendId`**, so two GPUs of one backend (VII + A770 are
  both Vulkan) are not representable there. The multi-device realize was built for one device per vendor (CUDA +
  Vulkan). **Whether two Vulkan devices can run one graph is NOT MEASURED**; the reading above says it cannot today.
- Cross-stage traffic: the two cards share no peer-to-peer path I can name, so a stage boundary is a device-to-host-to-
  device copy of one hidden-state tensor per token (`hidden x 4 B` = 20 KB at hidden 5120, **ARITHMETIC**); at decode
  that is small next to the weight reads, at prefill it scales with the prompt.
- Row 40 already asks whether per-stage placement exists on Vulkan; this audit's answer is: the placement type exists,
  the handle plumbing for two same-backend devices does not appear to, and a probe test settles it cheaply.
- GPU runners on both machines are wanted (CireSnave); that is infrastructure the PM and CireSnave own, with a Fuel-side
  test plan below.
