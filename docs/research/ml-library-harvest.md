# Ideas harvested from 23 ML libraries

Requested by CireSnave 2026-10-19: pick the ~20 most revolutionary ML libraries on GitHub, harvest the best ideas from each that would benefit Fuel without drastically changing its design, and add them to the roadmap for experimentation and likely addition. Docs only. Nothing here is started; the candidate rows are in `ROADMAP.md` item 17. Strata (separately requested) is in [`strata-ideas.md`](strata-ideas.md) / item 16.

## Method and limits (read before trusting a row)

- **Who read what.** Four research agents (Sonnet) each read a share of the libraries through `gh api` / web reads and checked every candidate against Fuel's `origin/main` at `9d0f97066467d5219e4a17c22602fadf957413e6` with `git grep` plus a positive control. Their full reports (refs, files read, "already in Fuel?" greps, rejected lists) are not committed; the pinned refs are in the table below. I then read all four reports, merged duplicates across libraries, and **re-ran the greps behind the claims I rely on most** (marked ✔ below). Everything else is the agents' finding, unverified by me.
- **Evidence is documentation and source excerpts, not benchmarks.** No library was built or run and no number here is a measurement. Several greps were path-limited (each agent named its pathspec): a concept under another name would be missed. Each row's experiment is a hypothesis with a metric, not a result.
- **Selection of the 23 is mine** (breadth over the layers Fuel cares about: compilers/IR, serving/KV, kernels, quantization, training memory, distributed). It is a judgment, not a ranking of "most revolutionary".
- **Scope filter** (`docs/architecture/09-non-goals.md`): rejected anything needing eager mode, MLIR-style multi-dialect IR, opaque custom ops, backend-internal fusion, runtime autotuning search, a serving engine, or a new primitive without a decisions-log entry. Foundation holds mechanism; orchestration and policy live in `fuel-inference` / `fuel-training` / consumers. Each row says which side it lands on.
- **Licences.** Ideas only; no code copied. Unsloth is AGPL-3.0 in several files (including its MoE kernels) despite an Apache-2.0 repo label; CUTLASS and Megatron-LM show NOASSERTION on GitHub. Anything adopted needs credit in its design note (CireSnave's provenance rule).

### E. Distributed (everything here hinges on one open decision)

`06-runtime.md` leaves open whether collectives are first-class graph ops or stay orchestrated above the graph. The libraries disagree in a useful way: **tinygrad lowers all-reduce to `Copy` + add + slice primitives (no new Op)**, while Megatron, MLX and Burn expose collectives as graph ops with conjugate backward rules (copy↔all-reduce, all-gather↔slice, reduce-scatter↔gather). Burn also launches the reduce the moment a parameter's gradient is final.

## Rejected (and why), consolidated

- **Eager capture / Dynamo graph breaks; `torch.library` and `mx.fast.metal_kernel` opaque ops; TVM BYOC / Triton on-demand user kernels** — eager-first and no `Custom` node.
- **Inductor/Triton/TVM/CubeCL codegen of fused kernels; MLX `compile_fuse`; IREE dispatch-region formation; ORT EP-compiled fused nodes; TensorRT-LLM plugin fusions** — backend-internal fusion; fusion is a registry recipe.
- **StableHLO/MLIR/IREE/vLLM-IR/Triton-TTIR dialect towers, tinygrad's "everything is a UOp", TE/TIR scheduling language** — multi-dialect IR (StableHLO import/export is already planned).
- **TVM MetaSchedule, tinygrad BEAM, Triton thousands-of-configs autotuning, TRT/vLLM runtime search** — "no autotuning search" non-goal (only H15/H16's bounded forms are proposed).
- **CuTe hierarchical layout algebra; stream-K; warp specialization; TMA pipelines** — kernel authoring is baracuda's (not ours to modify) or already in Phase 8 Tier 4.
- **EXL3 trellis/QTIP storage type** — needs a new `Encoding` variant, a KISS family, and non-owned kernels; revisit if a consumer needs ≤3 bpw beyond the IQ types (see also Strata S11).
- **Paged optimizers via CUDA managed memory (bnb)** — implicit demand paging against Fuel's planned residency; unavailable under WDDM (general knowledge, unverified).
- **Serving engines' schedulers, routers, disaggregated prefill, Mooncake store/transfer engine, jump-forward decoding, HTTP/MCP** — orchestration and networking above Foundation (non-goals; gaps G7, G8).
- **FSDP2/DeepSpeed ZeRO stage code, `shard_map`, per-rank process-group state** — training orchestration; Fuel uses explicit `DeviceGroup`/`SystemTopology` values and consumer-owned rendezvous.
- **Backend decorator stacks (Burn `Autodiff<Fusion<B>>`)** — strategy inside backends.
