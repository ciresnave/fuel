# Fuel's DEPENDENCY order, one crate per line:  <crate>\t<tier>\t<layer name>
#
# A crate may depend only on crates at its own tier or BELOW. Lower number =
# closer to the bottom (depended upon by more things, depends on less).
#
# ============================================================================
# THIS FILE IS A SOURCE, NOT A TRANSCRIPTION OF `docs/architecture/02-layers.md`
# ============================================================================
# 02-layers draws seven CONCEPTUAL layers and Rule 1 attaches the words
# "dependencies flow downward only" to that drawing. MEASURED 2026-09-02: the
# drawing's vertical axis is NOT the dependency axis, and taking Rule 1
# literally against it makes EVERY BACKEND a violator -- 6 of 6 backends
# depend on `fuel-ir`, which the drawing places ABOVE them. That is the backend
# contract working as designed: a backend must depend on the IR to implement it.
#
# The drawing's axis is CONSUMPTION / ABSTRACTION (hardware-proximity increasing
# downward, "users can stop at exactly the layer they need"), and its own prose
# says so -- "higher layers consume the Foundation surface but don't shape it"
# is about SHAPING, i.e. authority. Dependency runs the OTHER WAY across the
# Foundation/Backends boundary.
#
# So this file states the dependency order, which 02-layers does not state
# anywhere. It INVERTS the drawing across that boundary, deliberately. See
# GAP-265.
#
# Tiers are spaced by 10 so a crate can be inserted between two without
# renumbering the file.
#
# ---------------------------------------------------------------------------
# THIS FILE IS NORMATIVE, NOT DESCRIPTIVE. DO NOT "FIX" IT TO MATCH THE GRAPH.
# ---------------------------------------------------------------------------
# It states where crates SHOULD sit. A file transcribing the measured
# dependency depths would be SELF-SATISFYING BY CONSTRUCTION -- every edge
# legal, zero violations, forever -- and it would have printed a green on day
# one over the defect that hit Stage 2 as a hard cargo cycle.
#
# So a tier here MAY disagree with `cargo metadata`. That disagreement is the
# finding, not an error in the file. The allowlist is the measured gap between
# intent and reality, and it shrinks as the gap closes.
#
# ---------------------------------------------------------------------------
# ONE DELIBERATE DEVIATION FROM THE MEASURED GRAPH, AND IT IS THE POINT
# ---------------------------------------------------------------------------
# `fuel` (the facade) sits at tier 120, ABOVE the library crates. In the graph
# as it stands today it is BELOW them: measured dependency depth puts `fuel` at
# 9 and `fuel-nn`/`fuel-onnx`/`fuel-transformers` at 10, because those three
# depend on the facade. That is the inversion ROADMAP item 12 exists to undo.
#
# Placing `fuel` where it BELONGS rather than where it IS makes those three
# edges violations, which is what this gate is for. They are allowlisted with
# reasons; the allowlist may only SHRINK.
# ---------------------------------------------------------------------------

# ---------------------------------------------------------------------------
# FIVE CRATES CARRY NO TIER. THAT IS A DECISION, AND HERE IS WHAT IT COSTS
# ---------------------------------------------------------------------------
# An unassigned crate makes every edge it touches UNJUDGEABLE -- as source OR
# as target -- so the cost is stated as a MEASURED EDGE LIST rather than as a
# count of crates, which would hide it. 7 of 118 edges are unjudged
# and these are all of them:
#
#   fuel-core                   -> fuel-correctness-fixtures
#   fuel-correctness-fixtures   -> fuel-ir
#   fuel-datasets               -> fuel-core
#   fuel-examples               -> fuel-datasets
#   fuel-model-fixture          -> fuel-model-core
#   fuel-model-umbrella-fixture -> fuel-model-core
#   fuel-model-umbrella-fixture -> fuel-model-fixture
#
# `fuel-test-support` is the case that costs NOTHING, and it is recorded so it
# is not confused with the others: it participates in ZERO normal edges in
# EITHER direction. Its six consumers all take it as a [dev-dependency], which
# this gate excludes by design because a dev-dep does not constrain layering.
# Assigning it a tier would change no verdict. Measured, not assumed -- a draft
# of this header claimed all four fixture crates were dev-dep-only, and it was
# FALSE for two of them.
#
# `fuel-core -> fuel-correctness-fixtures` is the one to look at first: it is a
# NON-OPTIONAL [dependencies] edge (features serde, capture), so a fixtures
# crate sits on a production path. Consistent with FKC capture being production
# infrastructure, but it means the edge is real and wants a tier.
#
# The remaining four sit on ordinary edges and are placeable without a ruling.
# They are left out only because they were not needed to make the gate bite.
# Adding them is a STRICT coverage improvement for whoever does it next.
# ---------------------------------------------------------------------------
#
# `fuel-parallel` WAS on this list and is now placed at 130, and HOW it was
# placed is the point: it SELF-DECLARES its layer in its own module doc --
# `fuel-parallel/src/lib.rs:3`, "**Layer**: Use-Case Orchestration" -- which is
# ABOVE the facade, so its `-> fuel` edge is legitimate and needs no allowlist
# entry. That is evidence from the crate, not a judgement about it. The
# question was handed up rather than answered by picking a number, and the
# answer turned out to be written down already.
#
# Six crates declare a layer this way, out of 39 with a lib.rs. The gate now
# cross-checks all six against this file (see the arm in
# crate_dependency_direction.rs). The vocabulary DIFFERS from both the diagram
# and this file, so the mapping is written out explicitly there rather than
# inferred -- and `fuel-onnx` is recorded as a DECLARED DISAGREEMENT instead of
# being forced into a mapping: it says IO, 02-layers:76 says Interchange, and
# the dependency order puts it with the model libraries.
# ---------------------------------------------------------------------------
